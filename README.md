**The 3-minute pitch structure:**

| Time | What to Say | Why It Works |
|---|---|---|
| 0-30 sec | Problem hook | Judges care about problems, not features |
| 30-60 sec | Solution + demo | Show, don't tell |
| 60-120 sec | How it works | Technical depth without jargon |
| 120-150 sec | Impact + future | Shows vision and feasibility |
| 150-180 sec | Call to action | "Try it yourself" closes strong |

## Frequently Asked Questions

<details>
<summary><strong>❓ I'm a complete beginner. Can I still join hackathons?</strong></summary>

Yes. Many hackathons are beginner-friendly and have dedicated tracks for first-time builders.

**Your path:** `01-getting-started` → `02-find-hackathons` → `03-problem-selection`

Focus on learning and shipping something small. Don't try to build the next Google in 24 hours.

</details>

<details>
<summary><strong>❓ I don't know coding. Can I still participate?</strong></summary>

Absolutely. Hackathons need:

- **Designers** — UI/UX, wireframes, branding
- **Pitchers** — presentation, storytelling, public speaking
- **Researchers** — problem validation, market research, data analysis
- **Product thinkers** — feature prioritization, user flows, scope management
- **Content creators** — documentation, demo videos, social media

You can contribute without writing a single line of code.

</details>

<details>
<summary><strong>❓ How do I find teammates?</strong></summary>

Try these channels:

- **Discord communities** — MLH, Devfolio, and college hackathon servers
- **LinkedIn posts** — post that you're looking for a team
- **Devpost communities** — browse active hackathon forums
- **College groups** — WhatsApp, Telegram, or campus clubs
- **GitHub** — look for people with similar interests
- **Twitter/X** — use hackathon hashtags

See [12-team-building](12-team-building/README.md) for a full breakdown.

</details>

<details>
<summary><strong>❓ How do people actually win hackathons?</strong></summary>

Winning comes down to:

- ✅ Solving a **real problem** (not a random idea)
- ✅ Clean **UI** (judges notice this immediately)
- ✅ Fast **working MVP** (demos that crash lose)
- ✅ Strong **storytelling** (why should anyone care?)
- ✅ Proper **deployment** (a live link beats localhost)
- ✅ Clear **presentation** (3 minutes to be memorable)

Most teams lose because they overbuild or choose bad ideas.

See [15-winning-secrets](15-winning-secrets/README.md).

</details>

<details>
<summary><strong>❓ Can I use AI tools like ChatGPT, Cursor, Claude?</strong></summary>

Yes. Most hackathon teams now use AI for:

- Coding assistance and debugging
- UI generation and design
- Documentation and README writing
- Idea validation and research
- Pitch creation and scripting

**Tip:** Use AI to accelerate, not replace your thinking. Judges care about YOUR understanding.

See [07-vibe-coding-tools](07-vibe-coding-tools/README.md).

</details>

<details>
<summary><strong>❓ How do I choose a winning project idea?</strong></summary>

Don't build random ideas. Choose ideas that:

- Solve **real pain points** (would you use this yourself?)
- Are **easy to demo** (judges need to "get it" in 30 seconds)
- Have **visible impact** (tangible results beat abstract concepts)
- Can be **built in limited time** (scope kills more projects than bad code)
- Have **clear storytelling** (why does this matter?)

See [03-problem-selection-engine](03-problem-selection-engine/README.md).

</details>

<details>
<summary><strong>❓ What tech stack should I use?</strong></summary>

Pick speed over complexity. Here's the fast path:

| Layer | Recommendation | Why |
|---|---|---|
| Frontend | Next.js / React | Huge ecosystem, fast development |
| Backend | Supabase / Firebase | No backend setup required |
| AI | OpenAI / Gemini | Easy API integration |
| Hosting | Vercel / Railway | Free tier, instant deploys |

**Rule:** If you've never used it before, don't learn it at a hackathon.

See [05-tech-stack-chooser](05-tech-stack-chooser/README.md).

</details>

<details>
<summary><strong>❓ What if my project breaks during submission?</strong></summary>

Always have backups:

- 📹 **Demo video** — record a working version before submission
- 📸 **Screenshots** — capture every major feature
- 📊 **PPT** — slides that show what the project does
- 🔗 **Backup link** — deploy to a second platform
- 💾 **GitHub repo** — judges can see the code even if the deploy fails

See [10-deployment-mastery](10-deployment-mastery/README.md).

</details>

<details>
<summary><strong>❓ Can I participate solo?</strong></summary>

Yes. Many people win solo. But choose a smaller scope and move fast.

**Solo strategy:**
- Focus on **one core feature** (not ten)
- Nail the **presentation** (you're the whole team)
- Pick a **familiar stack** (no learning new tools)
- Build something **you can demo in 2 minutes**

</details>

<details>
<summary><strong>❓ How much time should I spend building?</strong></summary>

Follow the **60/20/20 rule:**

| Phase | Time | What You Do |
|---|---|---|
| Building | 60% | Core functionality, API integration |
| Polishing | 20% | UI cleanup, responsive design, edge cases |
| Demo + Pitch | 20% | Practice, slides, recording, deployment |

**Why?** Teams often lose because they spend everything on coding and ignore presentation.

</details>

<details>
<summary><strong>❓ Do judges check GitHub repositories?</strong></summary>

Sometimes yes. A clean GitHub repo increases credibility.

**What judges look for:**
- Clear README with screenshots
- Deployment links
- Clean commit history
- Documentation

Even if judges don't check, a good repo helps your team stay organized.

See [13-github-for-hackathons](13-github-for-hackathons/README.md).

</details>

<details>
<summary><strong>❓ Should I build something unique or practical?</strong></summary>

Practical usually wins. Judges care about:

- **Real problem** — does this solve something people actually face?
- **Execution** — does it work reliably?
- **Demo quality** — can you show it clearly?
- **Feasibility** — could this actually be built further?

"Crazy innovation" that doesn't work loses every time to a solid, practical solution.

</details>

<details>
<summary><strong>❓ How much should I rely on AI?</strong></summary>

Use AI to accelerate, not replace thinking.

**AI helps with:**
- Boilerplate code generation
- Debugging and error fixing
- Documentation writing
- Idea brainstorming

**You still need to:**
- Understand the architecture
- Make product decisions
- Present with confidence
- Handle Q&A from judges

Your understanding and execution still matter.

</details>
